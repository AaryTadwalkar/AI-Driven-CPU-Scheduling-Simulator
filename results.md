# Model Overview & Performance (copied from model_overview.md)

This document summarizes **all five trained models** and the **classical scheduling algorithms** used in the project, together with the datasets they were built on, training procedures, and benchmark results.

---

## 1. Decision Tree (DT)

- **What it does**: A supervised classifier that predicts the *best* scheduling policy for a given workload based on structural features (burst‑mean, CV, arrival dispersion, etc.). The output is a policy name (e.g., `SRTF`).
- **Training data**: `data/scheduling_dataset_S0.csv` (train split, seeds 0‑99 999). The file contains **6 501** workload records (see the line‑count query). Each record includes 12 engineered features and a label derived from the composite cost function.
- **Dataset size**: ~6 KB (CSV) – ~0.006 MB.
- **How it is created**: 
  1. Workloads are generated by the workload generator (Stage 3) and saved to `data/workloads.csv`.
  2. Feature extraction (`src/schedsim/ml/features.py`) runs **offline**, producing a CSV of features.
  3. Labels are computed by simulating all classical policies on each workload (Section 4c) and applying the composite cost.
- **Training command** (run from repo root):
  ```powershell
  python cli.py train-tree
  ```
- **Model file**: `models/decision_tree.joblib` (≈ 12 KB).
- **Performance (S0 test split, cs_cost = 0)** – from `results/final_comparison_S0.csv`:
  - Avg waiting = 26.05 ± 2.65 ticks
  - Avg turnaround = 33.93 ± 2.96 ticks
  - Avg response = 5.36 ticks
  - Effective makespan = 58.15 ± 3.23 ticks (same as baseline because DT adds **0 overhead** for inference)
  - Inference time **≈ 299 ms** per 100 k decisions (`inference_us_total = 299 040 µs`).
  - Overhead percentage of makespan: **0 %** (DT inference is negligible compared to the tick length used in the benchmark).

## 2. Random Forest (RF)

- **What it does**: Same task as the Decision Tree but using an ensemble of 100 trees, giving a stronger predictor at the cost of a larger start‑up latency.
- **Training data**: Identical to DT (`data/scheduling_dataset_S0.csv`).
- **How it is created**: Same feature pipeline; the training script builds a `RandomForestClassifier` with `n_estimators=100` and stores the model with `joblib`.
- **Training command**:
  ```powershell
  python cli.py train-forest
  ```
- **Model file**: `models/random_forest.joblib` (≈ 1 MB).
- **Performance (S0, cs_cost = 0)**:
  - Avg waiting = 26.07 ± 2.63 ticks
  - Avg turnaround = 33.96 ± 2.96 ticks
  - Avg response = 5.16 ticks
  - Effective makespan = 88.80 ± 3.26 ticks (significant due to **startup latency** of 31 193 µs per run, reflected in `overhead_pct_makespan = 42.14 %`).
  - Inference time **≈ 31 193 ms** per 100 k decisions.
  - Overhead: **42 %** of makespan, making RF unsuitable for low‑tick environments.

---

## 3. Tabular Q‑Learning (RL) – Model 3

- **What it does**: A reinforcement‑learning policy that learns a mapping from a **permutation‑invariant aggregate state** (ready‑queue length, shortest/longest remaining, etc.) to a **meta‑action** (e.g., *Shortest Remaining*). It chooses a process at each non‑forced decision.
- **Training data**: Experience generated by interacting with the simulator on the **training split** (seeds 0‑99 999) for both `cs_cost = 0` and `cs_cost = 1`.
- **How it is created**:
  1. `src/schedsim/rl/train.py` runs 20 000 episodes per seed, updating a sparse Q‑table (`dict`).
  2. Epsilon‑greedy exploration (`ε` decays geometrically).  
  3. The best checkpoint is saved as `models/q_table.pkl` and a human‑readable summary JSON.
- **Training command**:
  ```powershell
  python cli.py train-rl
  ```
- **Model file**: `models/q_table.pkl` (≈ 500 KB).
- **Performance (S0, cs_cost = 0)**:
  - Avg waiting = 16.74 ± 1.40 ticks
  - Avg turnaround = 24.62 ± 1.70 ticks
  - Avg response = 9.59 ticks
  - Effective makespan = 58.17 ± 3.23 ticks
  - Inference time **≈ 188 ms** per 100 k decisions (`inference_us_total = 187 550 µs`).
  - Overhead **≈ 0.01 %** of makespan – negligible.

---

## 4. Gradient‑Boosted Decision‑Tree Ranker (PID GBDT) – Model 4

- **What it does**: For each *process ID* (PID) it predicts a **candidate score** used to rank the ready queue. The policy selects the PID with the highest score (i.e., “PID‑GBDT”).
- **Training data**: Per‑candidate feature matrix `data/pid_bc_S0.npz` (and `S1` for `cs_cost = 1`). The file stores **≈ 6.3 M** bytes (~6.3 MB) of NumPy arrays with 13 observable features per candidate.
- **How it is created**:
  1. `src/schedsim/pidsel/features.py` extracts per‑process features during simulation on the training split.
  2. `src/schedsim/pidsel/gbdt_ranker.py` trains a `HistGradientBoostingRegressor` (scikit‑learn) on this data.
- **Training command**:
  ```powershell
  python cli.py train-pid-gbdt
  ```
- **Model file**: `models/pid_gbdt_S0.joblib` (≈ 700 KB).
- **Performance (S0, cs_cost = 0)**:
  - Avg waiting = 14.47 ± 1.32 ticks
  - Avg turnaround = 22.35 ± 3.42 ticks (effective)
  - Avg response = 13.16 ticks
  - Effective makespan = 100.24 ± 6.36 ticks (includes **large inference latency** of 42 625 ms per 100 k decisions, `overhead_pct_makespan = 37.08 %`).
  - Overhead: **37 %** – the model is accurate but costly.

---

## 5. Neural Candidate Scorer (PID NN) – Model 5

- **What it does**: A tiny PyTorch “Deep Sets” network (3 617 parameters) that maps per‑process features to a scalar score. Inference is exported to a pure‑NumPy weight file (`models/pid_scorer_S0_np.npz`) for zero‑runtime PyTorch dependency.
- **Training data**: Same as GBDT (`data/pid_bc_S0.npz` & `S1`).
- **How it is created**:
  1. `src/schedsim/pidsel/scorer_net.py` defines the network.
  2. `src/schedsim/pidsel/train_bc.py` runs DAgger (2 iterations) mixing the Oracle labels.
  3. After training, the network weights are saved as NumPy arrays (`*_np.npz`).
- **Training command**:
  ```powershell
  python cli.py train-pid-nn
  ```
- **Model file**: `models/pid_scorer_S0_np.npz` (≈ 1 MB).
- **Performance (S0, cs_cost = 0)**:
  - Avg waiting = 14.41 ± 1.30 ticks (matches SRTF within statistical noise)
  - Avg turnaround = 22.30 ± 1.74 ticks (effective)
  - Avg response = 13.41 ticks
  - Effective makespan = 60.62 ± 3.45 ticks (small overhead of **2.94 %**, inference time **≈ 2.94 s** per 100 k decisions).
  - Overhead: **~3 %**, making it the best trade‑off between accuracy and latency.

## 8. Dataset Ratios & Splits

| Split | Seed range | #workloads | Purpose |
|-------|------------|------------|---------|
| **Train** | 0 – 99 999 | 100 000 | Used to train the Decision Tree, Random Forest, and to generate per‑candidate features for PID models.
| **Validation** | 100 000 – 100 499 | 500 | Hyper‑parameter tuning for RL and PID models.
| **Test** | 200 000 – 200 999 | 1 000 | Final evaluation (the numbers in `final_comparison_*.csv`).

The **PID datasets** (`pid_bc_S0.npz` and `pid_bc_S1.npz`) are built from the *training* split with `cs_cost = 0` (S0) and `cs_cost = 1` (S1) respectively, yielding a **1 : 1** ratio of cost‑setting examples.

## 9. How the Models Choose a Policy

1. **Decision Tree / Random Forest** – Input: 12 workload‑level features → Output: policy name. The selected policy is executed **without additional per‑tick decisions**; the model incurs a **single upfront charge** (`on_start`).
2. **Q‑Learning** – At each non‑forced decision the current aggregate state is fed to the Q‑table; the action with maximal Q‑value is taken. Inference cost is incurred **per decision** (`decision_cost_us`).
3. **PID GBDT / PID NN** – For every ready process the per‑candidate feature vector is scored; the process with the highest score is selected. This also incurs a per‑decision cost.
4. **Oracle** – Uses the *true* composite‑cost label computed by exhaustive simulation of all 11 policies; serves as an upper bound.

## 10. Reading the Test‑Metric Summary (`final_comparison_*.csv`)

The CSV files in `results/` contain a row for each policy (classical + learned). Columns:

| Column | Meaning |
|--------|---------|
| **policy** | Identifier of the algorithm/policy (e.g., `FCFS`, `DT`, `PID_NN`). |
| **avg_waiting** | Mean waiting‑time per process, reported as `value ± stddev`. |
| **avg_turnaround** | Mean turnaround‑time (waiting + service) per process, `value ± stddev`. |
| **avg_response** | Mean response time (time from arrival to first CPU allocation). |
| **effective_avg_turnaround** | Turnaround after **AI overhead** is added (i.e., includes stall ticks caused by model inference). |
| **effective_makespan** | Total simulated time from first arrival to last completion **including AI stalls**. |
| **max_waiting** | Largest waiting time observed for any process in the workload. |
| **jain_fairness** | Jain’s fairness index for CPU time distribution (1 = perfectly fair). |
| **context_switches** | Number of context‑switch events triggered by the policy. |
| **decisions** | Number of *non‑forced* decisions where the policy actually had to choose a process (used for per‑decision cost). |
| **inference_us_total** | Total inference time **in microseconds** accumulated over all `decisions`. For classical algorithms this is `0`. |
| **overhead_pct_makespan** | `inference_us_total` converted to a **percentage of the makespan** (how much longer the schedule runs because of AI latency). |
| **gain_over_best_classical** | Difference in composite score vs. the best classical baseline (positive = better). |
| **gap_to_oracle** | How far the policy’s composite score is from the oracle (negative = worse). |
| **win_tie_loss** | Counts of workloads where the policy **won / tied / lost** against the oracle (e.g., `443/557/0`). |

### Quick interpretation example
- `PID_NN` row shows `overhead_pct_makespan = 2.93`. This means AI inference adds ~3 % extra time to the makespan compared with a pure‑algorithm run.
- `inference_us_total = 2 941 100` µs → about **2.94 seconds** of aggregate inference time for the 1 000 test workloads (≈ 2.94 ms per workload).
- `effective_makespan = 60.62` ticks vs. the baseline `58.15` ticks; the extra 2.47 ticks are exactly the AI‑induced delay.
